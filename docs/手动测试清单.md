# 手动测试清单（重启 dsh web 后执行）

> 宿主插件不走 HMR：**必须重启 `dsh web`** 才会加载本插件。重启后照此清单走一遍，
> 把结果记在文件末尾的「实测记录」里（这一步是可复用的人工作业脚本，也是后续优化的依据）。

## 0. 前置检查（不消耗对话额度）

```powershell
# 插件是否被加载：看插件行与工具是否注册
node <dsh目录>\node_modules\@deepseek-ai\dsh\lib\bin.js --profile web --dump-config | Select-String serendipity

# 只读接口是否活着（另一个终端）
curl.exe -s http://127.0.0.1:3080/api/dsh-serendipity/summary
```

期望：`--dump-config` 里出现 `id: serendipity / name: '@1603801678/dsh-serendipity'`；
`summary` 返回 JSON，`library.total` = 115。

## 1. 工具是否可见、是否会被自主调用

在 dsh web 里开一个新会话，说一句**不点名插件**的话，例如：

> 帮我设计一个小型解谜游戏的核心机制。

观察：
- [ ] agent 是否**主动**提到/调用 `serendipity_draw`（这检验系统提示词段落是否起作用）
- [ ] 若没主动调用，改成明确指令「先抽 5 条素材再设计」，确认工具本身可用

## 2. 闭环是否走完

- [ ] `serendipity_draw` 返回 5 条素材，且渲染里含「阅读要求」「桥接提示」「id」
- [ ] agent 读完后**主动**调用 `serendipity_note`（这是设计上的硬要求）
- [ ] **是否写出 `landed`**（本轮新增，最想看的一项）：对真的影响了工作的素材，agent 有没有指出
      结构**去了哪里**（哪个文件/哪一节、或改写了哪个决定）？还是只写一句「很有启发」？
      后者不计入统计——这正是设计意图，但要观察它会不会导致 agent 干脆不写落点。
- [ ] **落点是否可核对**：拿 agent 写的 `landed` 去实际文件里看一眼，那条结构真的在那里吗？
      这是本插件唯一能被人验证的信号，值得抽查几条。
- [ ] **「再看一眼」通道是否被用上**（本轮新增，最重要的一项）：draw 结果末尾可能出现
      「【当时没找到落点，值得再看一眼的】」，列出以前读过、当时没用上的旧素材。
      观察 agent 是**真的回去补记 `landed`**，还是每次都跳过这一段。
      如果长期跳过，说明这个动作太重，下一轮要改成插件更主动地追问。
- [ ] **`serendipity_stats` 里的「延迟兑现」段**：有落点之后去看一眼，
      「中位 X 天、最长 Y 天」是不是非零。**全为 0 就说明还没有证据**——
      目前记到的全是「立刻就能用上」的素材，不能据此宣称延迟兑现成立。
- [ ] **漏记提醒是否生效**：故意不记录，再抽一次，看是否出现形如
      `【dsh-serendipity】上一次 serendipity_draw 有 N 条素材还没有被记录：...` 的提醒

## 2.5 会话报告（2026-10-12 新增，最想验证的一项）

来历：一次开放式提问之后用户以为插件**一次都没抽**，实际是模型在第 23/60 步抽了 6 条、3 条写进交付文档。
本轮的改动就是让这件事**看得见**。重启 `dsh web` 后照做：

- [ ] **用开放式目标开场**（例如「帮我看看这个项目有没有可以改进的地方」），看 agent 是否
      **在第一轮就抽**，而不是先做一长串调查——这是本轮提示词改动的唯一目的。
      判断依据不要靠印象，用下面两条读：
- [ ] **`serendipity_stats` 的【本会话】段**：应出现形如
      「首次抽取在第 1 轮第 N 步（该轮开场后 X 分钟）；共抽 K 次／发出 M 条；记录 …」。
      **若这一步在第 1 轮且步数很小，说明改动生效。**
- [ ] **只读路由**：
      `curl "http://127.0.0.1:3080/api/dsh-serendipity/sessions?cwd=<项目目录>"`，
      看 `sessions[].firstDraw` / `draws` / `landed` 是否与实际调用一致。
- [ ] **离线复核**：把会话导出成 zip 后 `node tools/session-report.mjs <session.jsonl>`，
      两边的数字应当一致（一个读转录、一个读插件状态）。
- [ ] **设置开关真的关得掉**：在「设置 → 素材抽取（缪斯）」取消「会话报告」并保存，再抽一次——
      `projects/*.json` 里的 `sessions` 应**完全不新增**（不是只把显示藏起来），
      `/sessions` 返回 `enabled: false` 且 `sessions: []`。
- [ ] **补记不重复计数**：先记一批不带落点的笔记、再补记其中几条的 `landed`，
      【本会话】里的「条目」数不应翻倍，而落点数应当增加（这是延迟兑现的正常路径）。

## 3. 素材启发性（人工判断，最重要的一项）

抽 3~5 批（每批 5 条，换不同 `purpose`），请按这个标准打勾：

- [ ] 素材**读得懂**（`detail` 真的讲清了机理，不是一句事实）
- [ ] 素材**确实来自远处**（不是「换个说法讲同一件事」）
- [ ] `bridge` 提示**真的推动了思考**（不是套话）
- [ ] 至少有一批里出现了「这条确实能用」的素材

若整批都无感，记下是哪一类/哪几条，这决定下一步是扩库还是改抽取策略。

> **注意别用「当下用不上」判死刑。** 长期工作里素材的价值经常延迟兑现，
> 所以这一步看的是「读得懂、来自远处、推动了思考」，而不是「现在能不能直接用」。
> 插件本身也不再按「有没有用」学习（见 `README.md`「它优化的是覆盖度」）。

## 4. 三种模式的差异

- [ ] `violate: true`：抽出来的确实偏「打破假设/重定义问题」
- [ ] `bias: 生活观察`：生活类明显变多，但仍有其它领域（跨域不能被 bias 压掉）
- [ ] `bias: 反馈`（结构标签）：同类结构的素材变多

## 5. 记录与统计落盘

```powershell
# 项目记录（用会话的工作目录名找对应文件）
Get-ChildItem "$env:USERPROFILE\.dsh\dsh-serendipity\projects"

# 跨项目统计
Get-Content "$env:USERPROFILE\.dsh\dsh-serendipity\stats.json"

# agent 写的素材评估
Get-Content "$env:USERPROFILE\.dsh\dsh-serendipity\MATERIAL-MODEL.md"
```

- [ ] `projects/*.json` 里能看到抽过的素材、`hit`、`note`、**`landed`**（有的话）、`changedFrom`/`changedTo`
- [ ] `stats.json` 的 `noted` / `landed` / `selfReportedHits` 与实际情况一致
      （**三个数分别看**：`landed` 是写明地点的条数、`selfReportedHits` 是自评有用但**不计入统计**的条数）
- [ ] `MATERIAL-MODEL.md`（如果 agent 传了 `materialModel`）内容合理

也可以直接看接口（比翻 JSON 快），它把两个信号分开报：

```powershell
curl.exe -s http://127.0.0.1:3080/api/dsh-serendipity/summary | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>console.log(JSON.stringify(JSON.parse(s).usage,null,2)))"
```

### 测出来的一件重要事：agent 从不调用 `serendipity_note`

真实状态目录里：**41 次 draw、82 条素材发出、`noted: 0`、`hits: 0`**，82 条记录里
**没有任何一条带 `notedAt`**。也就是说抽取真的发生了，但记录完全没有发生。

影响：

- 素材不会被标记为已读 → 池子抽干前，去重实际上失效（下次仍可能抽到同一条）；
- 统计恒为 0 → 覆盖度学习拿不到样本，那个功能处于休眠状态。

已做的应对：把漏记提醒的措辞改得更具体——现在明确说明「不记录会导致素材不被标记为已读，
且插件无法统计哪种结构的素材真的有用」。提醒同时出现在两处：draw 结果里的阅读要求、
以及下一次 draw 的 deferred context。

**已复测**：后续会话改为每次必记（有一次会话连记 5 条、映射质量很高，例如「峰值约束→通关判据」
「非交换→藤蔓」）。当前真实数据：**123 条读取记录、11 条笔记、其中 1 条写明落点、9 条自评有用**。
「11 条里只有 1 条落点」是预期内的——落点比自评难写得多，而它正是唯一能被人核对的信号；
需要继续观察 agent 会不会因为「写了自评也不算数」而干脆不写（见上方第 2 节的检查项）。
