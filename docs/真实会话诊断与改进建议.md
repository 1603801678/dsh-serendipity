### 1.2 关键失败点（原文）

**（a）网络素材的落点被系统性丢弃 —— 本轮最重要的一条**

模型在项目文档里为 7 条外部结构写明了落点（`设计/内容拓展_v2_近期灵感.md` 附录 C，
6 条有落点、1 条因 403 落空）。它两次尝试把这批记录交给插件：

```
seq 104208  serendipity_note(8 条)
  → Error: invalid arguments: missing required property "items[0].id"; … "items[6].id"
     （整批 8 条一起失败，schema 校验在 execute 之前，插件代码没有机会容错）

seq 105642  serendipity_note(7 条，id 用了自己起的名：ext-gstone-0prob / ext-gcores-189886-bridge / …)
  → 已记录 0 条。
     未识别 id（未写入）：ext-gstone-0prob, ext-gcores-189886-bridge, …（7 个全列）
```

模型的结论（原文，seq 106136 / 107322）：

> Note only accepts IDs from the plugin's own draw system, so external content can't be noted directly
> ——that's fine since it wasn't drawn.
> 外部来源的 id 插件不认（只认它自己抽出的素材），但结构已经入库，下次做设计类任务会再抽到。

**它的自洽结论是错的，而插件把这个错误结论引导得很好**：插件说「未识别」却不说「你该怎么办」，
于是模型判定「这是设计如此」，放弃了 6 条落点——包括它自己评为「本轮最重」的那三条
（零随机的真实缺陷 / 通解禁忌 / 能量换算律）。

**（b）schema 的整批拒绝**

`items[].id` 在 schema 里是 `required: true`，而校验发生在 execute 之前，所以**任何一条缺 id，
整批全废**。这不是理论风险：seq 104208 一次丢了 8 条。而且模型看不出「少填了 id」与
「这个 id 不认识」的区别——两次都只看到一句它无法据此修正的话。

**（c）fetch 的有效率**

| 结果 | 次数 | 具体 |
| --- | --- | --- |
| ✅ 有用 | 6 | 雷科技访谈、游资网、3楼猫、**集石论坛帖**、机核 `/articles/189886`、机核 `/articles/212986` |
| ❌ 撞墙 | 4 | `zhuanlan.zhihu.com` 403、`ngabbs.com` 403、`jump2.bdimg.com` 403、`archive.org` 超时 |
| ⚠️ 拿到但无用 | 3 | 机核**首页**（236KB 全是导航与新闻标题）、GitHub 搜索 JSON（预算被 `*_url` 字段吃光）、arXiv（**OR** 语义 → 57 万条无关结果） |

模型自己总结出的正确姿势（seq 88361）：

> 我先试了抓首页和 GitHub 搜索，**两条都是浪费**……有效的路径是**先用 `web_search` 找到具体文章页，
> 再抓正文**。……arXiv 那个接口有个坑：关键词用空格分隔会被解析成 `OR`，得用 `all:"phrase"`。

**这两条「正确姿势」应该写在 `lib/fetch.js` 的工具说明里，而不是让每个项目重新发现一次。**

### 1.3 量化：被丢掉的落点有多少

直接读插件在该项目下的真实状态（`~/.dsh/dsh-serendipity/projects/p-e15f8804-卡牌测试.json`）：

| 口径 | 数字 |
| --- | --- |
| 该项目在插件里的条目 | 19 条（19 条有笔记） |
| 其中写明落点的 | **14 条** |
| **本次会话（2026-10-10）由 draw 产生并被记下的新落点** | **3 条**（捕食者-猎物周期 / 杰文斯悖论 / 对称性导出守恒律），另有 1 条修正（规模不经济） |
| **本次会话已经落进项目文档、但插件拒绝记录的落点** | **6 条**（`内容拓展_v2_近期灵感.md` 附录 C 的六行） |

## 3. 四个方向的具体改进建议

编号后面括号里是成本（低/中/高）与我的推荐度。

### 3.1 更多的信息来源

**建议 A：可达性从「写死的清单」改成「插件自己的记忆」（成本：低，推荐：★★★）**

现状是 `lib/fetch.js` 里两份常量字符串数组。证据表明它会过时、而且被模型绕过
（模型把可达性表写进了项目文档）。做法：

- 状态目录新增 `sources.json`：**按 host** 记 `{ ok, status, lastCheckedAt, kind, note }`。
- `fetchReadable` 每次调用后更新它（成功/失败都记，失败记状态码）。
- `fetch` 的渲染里输出「本机实测：✅ 最近成功 / ❌ 403 / ⚠️ 只抓到导航」，
  **优先用实测记录，常量清单只作初始种子**。
- 附带一条已经踩到的规则：**`zhihu.com` 200 而 `zhuanlan.zhihu.com` 403，所以键必须是 host**。

这条把「清单维护」从人工改成自动，且让插件越用越准。

**建议 B：清单按「来源类型」重构，并加上搜索端点（成本：低，推荐：★★★）**

把现有 6 条常量扩成三组（实测结果见附录 A）：

- **网页来源**（要文章页，不要首页）：机核 `/articles/<id>`、B站 `/read/cv<id>`、集石 `/bbs/discuss-*`、
  3楼猫、游资网、雷科技、游研社、indienova、少数派、果壳、科学网、环球科学、
  Quanta / Nautilus / Aeon / 99% Invisible / The Marginalian / Phys.org / ScienceDaily / MIT News。
- **搜索端点**（插件**自己就能搜**，不必依赖宿主）：B站专栏搜索 API、少数派列表 API、
  Crossref/OpenAlex/arXiv/GitHub/StackExchange/PubMed。
- **随机源**：萌娘百科 `list=random`（唯一实测可达的「随机词条」入口）。
- **不可达**：把上面 §2.2 那份写进去，并注明「按 host、按页型」。

**建议 C：给 `fetch` 加一个「找页」的前置能力（成本：中，推荐：★★）**

会话里 agent 花了 3 次 `web_search` **只为了拿到 URL**。可加 `serendipity_fetch({ query })`：
在没有 `url` 时，用上表里的搜索端点点拼出 3~5 个候选并返回标题+URL+日期，由模型再挑一个抓正文。
注意边界：这仍然只走**本机可达**的端点，不引入通用搜索引擎。

### 3.2 更新的信息

**建议 D：`learn` 记来源与时间，`draw` 增加一条「新」的轴（成本：低-中，推荐：★★★）**

- `serendipity_learn` 增加可选 `sourceUrl`，落盘写 `learnedAt`（现在只有文件 mtime）。
- `draw` 增加 `fresh: true`（或 `scope` 再加一档）：**仅在有证据时生效**——
  对 `learnedAt` 在 N 天内的沉淀素材给**有界**抬升（建议 ×1.3，和覆盖度权重同量级、同样不进过滤器）。
  依据：沉淀素材现在几乎抽不回来（115 条内置 vs 个位数沉淀，纯概率下要几十次抽取才轮到一次），
  等于「沉淀」这个动作没有回流路径。
- `stats` 增一行「最近沉淀 N 条（最近一条 X 天前）」——这是「新」唯一可观察的证据。

**建议 E：`discover`：把「最新」变成可执行的步骤（成本：中，推荐：★★）**

不改 `draw` 的随机性，而是加一个**面向来源**的入口：给定 `topic` 与 `since`（默认 30 天），
拼接 2~3 个**带日期排序**的搜索端点（B站专栏搜索、少数派列表、OpenAlex/arXiv/Crossref 按时间倒序），
返回候选清单。这把会话里「用手工 13 次 fetch 试探」压成一次。风险：中文社区多数没有公开搜索 API，
所以 B站搜索 + 少数派列表是主力，其余要靠 `web_search` 兜底。

**建议 F：语料补日期（成本：低，推荐：★）**

内置 115 条是「常青」素材，**给它们编日期是伪造**。所以不建议加 `date` 字段，
只在**沉淀素材**上记时间——即「新」只对 `source: user` 的那部分有意义。这一条是为了防止
将来为了「新」而给常青素材贴上假时间戳。

### 3.3 更随机的素材

现状：随机性全部发生在**115 条固定池子**内部（加权抽样 + 拥挤惩罚 + `bias/avoid/violate`）。
三个方向可以显著扩大随机面：

**建议 G：领域 × 结构核心 的随机配对生成（成本：低-中，推荐：★★★）**

插件已经有两个可枚举的轴：**114 个来源领域**与 **76 个结构核心**。加第三样东西——
一份**领域地名志**（数百个具体学科/工种，如「冰川学 / 港口调度 / 消防工程 / 织造工艺 / 戏曲锣鼓 /
蜂群管理 / 冰川钻探 / 电梯调度」），然后随机抽一对（未覆盖的领域 × 未读的结构核心），
返回的不是素材而是一句**生成任务**：

> 「去『消防工程』里找一件体现『阈值 + 延迟』的事，写出它的**机理**（为什么有效/为什么反直觉），
> 提炼成一条可迁移结构，再用 `serendipity_learn` 沉淀。」

为什么这条最值：**素材的作者成本是零**（模型自己写），来源面是**无界的**（地名志可扩到几千条），
而且它天然产出「新」素材。会话已经证明模型能做这件事——它从 6 篇外部文章里提炼出了合格的
结构（`serendipity_learn` 4 次全部通过校验）。差别只是：**这次由插件随机选领域，而不是由搜索引擎决定**。

**建议 H：随机词条源（成本：低，推荐：★★）**

`萌娘百科 random API` 实测可达。这是唯一不依赖宿主搜索的「真随机入口」。
它抓回来的东西**必然与问题无关**——而这正是插件的卖点（「大部分会落空，比例本身就是重点」）。
可作为 `fetch({ random: true })` 或 `discover` 的一个源。

**建议 I：把随机源做成可插拔（成本：中，推荐：★★）**

现在「随机」= 对内置数组做加权抽样。建议抽出一个 `RandomSource` 概念：
`corpus`（默认）/ `learned`（只在沉淀素材里抽）/ `generated`（建议 G）/ `web`（建议 H）。
这样「随机」不再是单一实现，将来加源不用动抽取引擎。

### 3.4 更有意思的关联

这一项我认为**投入产出比最高**，因为现有引擎恰恰在**阻止**本轮最有效的关联方式。

证据：本轮最好的成果来自**两条素材的对撞**——用「捕食者-猎物周期」去修「派别是纯正反馈」，
并且模型**同时**看到了「饱和」与「延迟」两个反方向修法才做出取舍（seq 87126 的 `note`）。
而 `lib/draw.js` 的 `crowdingPenalty` 对**共享结构核心**的候选罚 ×0.55 / ×0.15——
一次抽取里**不允许**出现同一个结构的两个实例。也就是说：**当前引擎最优化的「分散」，
恰好排除了「同一形状在两个远域里的两次出现」这个最强的类比信号。**

**建议 J：`collide`（碰撞对）——同结构、异来源的成对抽取（成本：低，推荐：★★★）** —— ✅ **已实现（同日六轮）**

`draw({ collide: true })` 返回**一对**：结构核心相同（或相邻）而来源领域距离最远的素材，
渲染成「同一个形状在两个不相干的领域里各出现了一次：把它们和你手上的问题摆在一起」。
实现上是把 `crowdingPenalty` 在结构维度上**反向**，同时把来源维度罚得更狠。成本很低，
因为它用的是已有的索引（`structureTags` × `origin`）。

**建议 K：`tension`（张力对）——两条给出相反预测的素材（成本：低-中，推荐：★★★）**

会话里模型自己面对的正是这种取舍：**饱和**（快反馈）对**延迟**（迟滞），
它选了一个、把另一个留给别的舞台。如果语料能声明「对立核心」，插件就能**故意**递上一对
相反预测，逼出一次显式的取舍——这比再给一条同向素材有价值得多。

做法：在 `lib/structure-tags.mjs` 旁加一张**对立表**（约 15~25 对，人工维护、lint 校验两边都存在），
例如 正反馈/负反馈、饱和/延迟、阈值/连续、冗余/精简、放大/抑制、锁定/可逆。
`draw({ tension: '饱和' })` 返回 `[饱和实例, 延迟实例]` 并要求写明「你的问题更靠哪一边、凭什么」。

**建议 L：`chain`（走链）——沿结构核心走两步（成本：低，推荐：★★）**

素材 A → 取它的一个结构核心 → 找**另一个领域**里用同一核心的素材 B → 再取 B 的**另一个**核心 → 素材 C。
这是文献里说的 bisociative network（`docs/同类工作调研与改进建议.md` 参考链接里就有这篇）。
纯图遍历，没有作者成本，且天然产生「意料之外的邻居」。

**建议 M：把 `MATERIAL-MODEL.md` 回流进 draw（成本：低，推荐：★★，但有反作用风险）**

模型写下的 `materialModel` 已经是**语料的自我批判**，但只在 `stats` 末尾被回显一次。
建议在 `draw` 的阅读要求里带上一句「上一次你对本库的判断是：……（N 天前）」。
**风险必须一起处理**：这是一条自我强化的回路——模型写「该 bias 形式系统」，下一轮它就更可能
bias 形式系统，覆盖度就真的偏了。所以要么只作**展示**、且与覆盖度提示并列（「上次的判断是这样，
但覆盖度说这些核心你还没读过」），要么明确写成「上一次的判断不构成对本轮抽取的约束」。

### 3.5 顺带：`decompose` 为什么一次没被调用

它出现在系统提示词里（`lib/index.js` 第 242 行），但**不在 `draw` 的协议里**，
而 `draw` 才是模型每次真正读的那段文字。本轮任务（拆解一个卡牌游戏、判断「洗牌是不是必要的」）
与它**逐字对口**，模型却手工做了这件事。

建议（成本：低）：在 `draw` 的渲染里加一行条件提示——当 `purpose` 里出现「设计/拆解/重做/改造」
这类词而本项目还没用过 `decompose` 时，提示「先把部件列出来再抽，`serendipity_decompose` 会强制
你对每个部件回答『去掉它、或者换成别的』」。这是**一次性**提示，不能变成每次都说。
